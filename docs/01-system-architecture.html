1. เป้าหมาย ขอบเขต และ Non-Goals

Goals

• Non-custodial 100% (ผู้ใช้ถือ key เอง)
• Gasless สำหรับผู้ใช้ (Solver จ่าย gas)
• AI ตัดสินใจขนาดการซื้อ/จังหวะ ภายใต้ caveats บนเชน
• Blast radius ของการโดนแฮกฝั่ง server จำกัดที่ งบต่อรอบ เท่านั้น
• ทำเงินจริงภายใน 3 เดือน ด้วยต้นทุน ≈ $0 และไม่ต้องมีใบอนุญาต (Phase A ไม่แตะหลักทรัพย์)
• Multi-asset ผ่าน PairRegistry: Phase A = ETH/cbBTC; Phase B = tokenized stocks ผ่าน partner

Scope (Stage 0 → Phase 1)

• Phase A asset: USDC → WETH, cbBTC (curated list) บน Base ผ่าน Uniswap v3 / Aerodrome — permissionless, 24/7, liquidity ลึก (ADR-011)
• Chain: Base (+ Base Sepolia)
• Phase B (ภายหลัง): tokenized US stocks/ETF บน TSV ผ่าน partner ที่มีใบอนุญาต; module eligibility/venue-hours เตรียมเป็น plug-in (ADR-012) ไม่เปิดใน Phase A
• Web app + MetaMask/WalletConnect (EOA/Safe; ERC-4337 passkey ที่ T0 — ADR-010)
• Telegram bot (alerts + NL strategy)
• 3 deployables: core · exec · signer (หัวข้อ 4.1)

Non-Goals

• ไม่ทำ custody/omnibus wallet ใดๆ
• ไม่ทำ cross-chain bridging ใน Phase 1
• ไม่ให้ LLM ส่งธุรกรรมโดยตรง (LLM = advisor, policy engine = decider, chain = enforcer)
• ไม่รับ fiat on-ramp เอง (ใช้ partner)

1.1 Legal posture (v3.0): "software + protocol" ไม่ใช่ "บริการซื้อขายแทน"

ความจริงที่ต้องยอมรับ: กฎ broker-dealer/adviser (US) และ digital-asset business / การชักชวนลงทุนหลักทรัพย์ต่างประเทศ (ก.ล.ต. ไทย) ไม่มี de minimis — "เล็ก" ไม่ช่วย สิ่งที่ช่วยคือโครงสร้าง
หลักทำอย่างไรใน Phase A
ไม่ใช่หลักทรัพย์สินทรัพย์ Phase A = ETH, cbBTC (crypto ที่ไม่ใช่ security ตามแนวปฏิบัติปัจจุบัน) — ไม่แตะ tokenized stock/RWA ที่เป็นหลักทรัพย์จนกว่าจะถึง Phase B
Software, not serviceสัญญาเป็น open-source, permissionless, non-upgradeable; ใครก็รัน agent/solver ได้ (self-host guide + Docker image); hosted agent ของเราเป็น "ความสะดวก" ไม่ใช่การจัดการทรัพย์สิน
ผู้ใช้ตัดสินใจเองRules ทุกข้อผู้ใช้ตั้งเอง (rule builder/BYO-LLM); ระบบไม่มี "คำแนะนำ" — ไม่มี default portfolio, ไม่มี recommended asset, ข้อความทั้งหมดเป็น factual (ราคา, gas, สิ่งที่กฎของคุณสั่ง)
ไม่ถือทรัพย์สินNon-custodial ทุกชั้น; เงินไม่เคยอยู่ในสัญญาข้ามบล็อก; fee หักบนเชนไป Treasury ตาม FeeModule ที่เปิดเผย

2. หลักการออกแบบ (Architecture Principles)

Principleความหมายในทางปฏิบัติ
P1 · Chain is the enforcerทุกกฎที่ปกป้องเงินผู้ใช้ (budget/period, token pair, recipient = user, expiry, nonce) ต้องบังคับใน RwaDcaSettlement.sol เท่านั้น ระบบ off-chain ใดๆ ถือว่า "อาจถูกยึดได้"
P2 · Off-chain is untrusted by designAgent, Solver, LLM, DB ทั้งหมดถูกออกแบบให้ถ้าถูกยึดครองแล้วสูญเสียได้สูงสุดเท่ากับ 1 period budget ต่อผู้ใช้ และ solver hot-wallet balance ของเราเท่านั้น
P3 · Determinism before intelligenceLLM (ของผู้ใช้เอง, BYO) ทำหน้าที่แปล NL → structured rules เท่านั้น; signal ทั้งหมด deterministic การตัดสินใจสุดท้ายผ่าน deterministic policy engine ที่ replay/audit ได้ (input → decision เดิมเสมอ)
P4 · Isolate the signerSession key ของ agent อยู่ใน signer service แยก network, ไม่มี inbound จาก internet, มี allowlist ของ EIP-712 typed data ที่รับเซ็นได้ (domain, contract, tokenIn/out, max amount)
P5 · Idempotent everywhereIntent มี nonce เดียว ใช้ครั้งเดียว; ทุก job/worker ทำซ้ำได้ปลอดภัย; reconciliation กับ on-chain state เป็น source of truth
P6 · Observable & auditableทุก decision มี trace: market snapshot → rules → decision → intent → tx → settlement event เก็บถาวรใน immutable audit store
P7 · Progressive decentralizationเริ่มจาก solver ของเรา (permissioned) → เปิดให้ solver ภายนอกแข่งขันผ่าน allowlist → permissionless พร้อม surplus-sharing

7. Smart Contract Layer — Production Hardening

สัญญาจาก workshop (RwaDcaSettlement.sol) มีแกนถูกต้องแล้ว: configureDcaAgent, revokeAgent, settle, _enforceCaveats, usedNonces, และ error set (PeriodBudgetExceeded, LifetimeBudgetExceeded, UnauthorizedTokenPair, InsufficientOutput, …) สิ่งที่ต้องเพิ่มเพื่อ production:

Batch settlement

settleBatch(Intent[] intents, bytes[] sigs) loop เรียก logic ของ settle รายตัวใน try/catch — intent ที่ revert ปล่อย DcaOrderSkipped(user, nonce, reason) โดยไม่ล้มทั้ง batch; invariant: ผลลัพธ์ต่อ intent ต้องเท่ากับการเรียก settle เดี่ยว (nonce, budget, balance check) — ทดสอบด้วย differential fuzz. ลด gas/user 40–60%

Modular contracts

RwaDcaSettlement (core, immutable) + SolverRegistry (allowlist/permissionless toggle + bond) + FeeModule (volume fee bps, surplus split 80/20, cap ต่อ tx) + PairRegistry (allowed tokenIn/tokenOut ต่อ chain)

Signature & accounts

EIP-712 domain ผูก chainId + contract; รองรับ EIP-1271 เมื่อ intent.user เป็น Safe/AA; agent key เป็น EOA session key; ตรวจ deadline ≤ now + maxTTL

Upgrade policy

Core ไม่ upgradeable (ลด governance risk). Migration = deploy ใหม่ + ให้ผู้ใช้ re-delegate (มี UX migration wizard). Registries/Fee เป็น Ownable โดย Timelock (48h) + Safe 3-of-5

Circuit breaker

pauseSettle() โดย Guardian (2-of-3) หยุดเฉพาะ settle ใหม่; revokeAgent ของผู้ใช้ทำงานเสมอ แม้ pause (non-custodial guarantee)

Period accounting

Fixed windows แทน rolling เพื่อ determinism แต่ ไม่ epoch-aligned ร่วมกันทุกคน: periodStart ของแต่ละ delegation = เวลาที่ configure (หรือ offset = uint(keccak(user)) % period) เพื่อกระจาย window reset ของผู้ใช้ทั่วสัปดาห์ — ป้องกัน thundering herd ที่ทุกคน "ซื้อได้" วินาทีเดียวกัน; เก็บ spentInPeriod, spentLifetime; ป้องกัน overflow/rounding ด้วย 6-dec USDC ↔ decimals ของ tokenized share

Fee accounting

Fee หักจาก surplus (received − minOut) และ/หรือ bps จาก amountIn ตามที่ประกาศบนเชน; ผู้ใช้เห็นค่าธรรมเนียมสูงสุดใน delegation preview; fee recipient = Treasury Safe

Assurance plan

  • Tests: unit (Foundry), fuzz + invariant tests (เงินผู้ใช้ไม่ออกนอกเส้นทาง, nonce ใช้ครั้งเดียว, settleBatch ≡ settle รายตัว, budget monotonic), fork tests กับ Uniswap v3/Aerodrome บน Base mainnet fork (Phase B: TSV pool เมื่อเปิด)
  • Static/formal: Slither, Aderyn, Certora/Halmos สำหรับ invariants หลัก 3 ข้อ
  • Audit: 2 บริษัทอิสระ + public contest (Code4rena/Sherlock) ก่อน mainnet; bug bounty (Immunefi) หลัง launch
  • Deployment: deterministic (CREATE2) เพื่อ address เดียวกันทุก chain; verified source; Deployment record ใน repo
  • Adapters: Phase A = UniswapV3Adapter/AerodromeAdapter (permissionless); Phase B = TSVPoolAdapter ที่ต้องถูก venue allowlist + eligibility check ของ intent.user; PairRegistry เก็บ (adapter, pool, tokenIn, tokenOut, flags: permissioned/hoursSource)

9. Solver & Execution Layer

  • Routing (v3.0 — Phase A DEX): USDC → WETH/cbBTC ผ่าน Uniswap v3 หรือ Aerodrome บน Base (quote ทั้งสอง เลือก amountOut สูงสุดหลังหัก gas); pool ลึกระดับหลายสิบล้านดอลลาร์ → order $50 slippage ≈ 0. Phase B: TSVPoolAdapter ผ่าน partner (permissioned)
  • Prerequisite (Phase A): ไม่มี — pools มีอยู่แล้ว 24/7; alarm slippage รายวันยังคงไว้; Phase B prerequisite (venue เปิด, รับ adapter, รับผู้ใช้, depth) ย้ายไปหัวข้อ 1.2
  • Simulation gate: ทุก tx ต้องผ่าน eth_call (และ debug_traceCall เมื่อมี) ที่ block ล่าสุด และตรวจว่า balAfter − balBefore ≥ minOut ก่อนส่งจริง
  • MEV protection: ส่งผ่าน Flashbots Protect / MEV Blocker (Ethereum) หรือ sequencer โดยตรง (L2) พร้อม tight deadline และ minOut
  • Pass-through model: solver ไม่ถือ inventory และไม่มีความเสี่ยงราคา — ใช้ USDC ที่สัญญาดึงจากผู้ใช้ภายใน callback ไป swap บน DEX ทันที (atomic) แล้ว token เข้ากระเป๋าผู้ใช้ใน tx เดียว; ถ้า output < minAmountOut ทั้ง tx revert. ทุนที่ solver ต้องมี = gas float เท่านั้น (ดู หัวข้อ 9.1)
  • Gas policy: EIP-1559 maxFee = min(2×baseFee + tip, cap); replacement ทุก N blocks; ค่า gas ที่จ่ายถูกบันทึกเพื่อคำนวณ unit economics ต่อ user
  • Multi-solver (Phase 3): intent feed แบบ auction สั้น (2–5 s) ให้ solver ภายนอกเสนอ amountOut; ผู้ชนะ settle; surplus แบ่ง 80/20 ผ่าน FeeModule; solver ต้องวาง bond ใน SolverRegistry

12. Reliability, Idempotency & Reorg Handling

  • Exactly-once settlement เกิดจากสัญญา (usedNonces) ไม่ใช่จาก infra; infra จึงเป็น at-least-once ได้อย่างปลอดภัย
  • Elastic in time: ทุก cycle มีทั้ง period ให้ทำ — scheduler กระจาย next_run_at ทั่ว window (jitter) และจัด priority ให้ user ที่ window ใกล้ปิดก่อน; load spike จึงกลายเป็น "ซื้อช้าลงหลายชั่วโมง" ไม่ใช่ล่ม (capacity model ใน 02 หัวข้อ 15c)
  • Single in-flight intent per user ผ่าน pg_advisory_xact_lock + DB unique constraint (user, period_start) เพื่อลด revert ที่ไม่จำเป็น
  • Nonce scheme: nonce = keccak(user, periodStart, attempt) → replay ข้าม period ไม่ได้ และ attempt ใหม่มี nonce ใหม่
  • Finality: L2 ใช้ safe สำหรับ UI, finalized สำหรับ accounting/fee; Ethereum ใช้ 2 epochs
  • Job versioning: job payload มี schema_version; worker ใหม่ต้องรัน payload เก่าได้ (expand/contract); deploy = drain → swap
  • Graceful degradation: data provider ล่ม → ใช้ fallback source; ล่มทั้งหมด → SKIP (ไม่ซื้อ) และแจ้งเตือน — ไม่มี "default buy" เมื่อไม่มีข้อมูล
  • Multi-RPC: ≥ 2 providers (own node ที่ T4); health-check quorum สำหรับ block head; ถ้าแตกต่าง > 2 blocks → alert

15.1 ADR-010 รายละเอียด: MetaMask หรือ Telegram?

คำถามนี้จริง ๆ คือ "key ของผู้ใช้อยู่ที่ไหน" ไม่ใช่ "UI อยู่ที่ไหน" — Telegram เองไม่ใช่ EVM wallet: Wallet/TON Space ในตัว Telegram เป็นเชน TON (ไม่มี USDC/tokenized stocks บน EVM) ดังนั้น "ใช้ผ่าน Telegram" หมายถึง Telegram Mini App + embedded EVM wallet (passkey smart account หรือ MPC provider) เสมอ

เกณฑ์A · MetaMask / WalletConnect (web app)B · Telegram Mini App + passkey smart account (ERC-4337)C · Telegram Mini App + MPC embedded wallet (Privy/Web3Auth ฯลฯ)
Non-custodial ตรงตาม pitch✅ key อยู่กับผู้ใช้เต็มรูปแบบ✅ key = passkey บนอุปกรณ์ผู้ใช้ (Secure Enclave), account เป็น contract ของผู้ใช้⚠️ key แบ่งส่วนกับ provider (TEE/MPC) — ผู้ใช้ควบคุมได้แต่พึ่ง vendor; ต้องมี export path
Onboarding คนทั่วไป (ไทย)❌ ต้องติดตั้ง extension/app, seed phrase, มี ETH+USDC บน Base เอง✅ ไม่มี seed phrase, ไม่มี extension, เปิดจาก Telegram ได้เลย; setup tx sponsor ผ่าน paymaster ได้ (เราออกค่า gas หลักสตางค์)✅ เหมือน B + social login
ค่าใช้จ่าย / vendor$0 · ไม่มี vendor$0–low · ใช้ open-source account stack (เช่น Coinbase Smart Wallet / ZeroDev + passkey) + paymaster ที่เราจ่ายเองMAU-based pricing หลัง free tier + vendor lock-in
งานฝั่ง solo devน้อยที่สุด: wagmi + viem, มีอยู่ใน 01 แล้วปานกลาง: Mini App (React ใน Telegram WebView), 4337 bundler/paymaster, EIP-1271 ตรวจลายเซ็นใน contract (รองรับแล้ว)ปานกลาง + SDK vendor

คำตอบ: ทำ A ก่อน (Stage 0) เพราะฟรี ไม่มี vendor และตรงกับผู้ใช้กลุ่มแรกที่มี USDC บน Base อยู่แล้ว โดยให้ Telegram เป็น bot (แจ้งเตือน, สั่ง strategy ภาษาคน, deep link ไปเซ็นใน web) — สองอย่างนี้รวมกันได้ทันทีด้วยของที่ออกแบบไว้แล้ว. เมื่อถึง T0 (มีผู้ใช้จ่ายเงิน) ค่อยเพิ่ม B เป็น onboarding path สำหรับคนทั่วไป: Telegram Mini App + passkey smart account + paymaster — ไม่ต้องแก้สัญญาเพราะรองรับ EIP-1271 อยู่แล้ว. หลีกเลี่ยง C เป็น default เพราะขัดกับ positioning "non-custodial 100%" และมี MAU cost. ทั้ง A และ B อยู่หลัง abstraction เดียวกัน (EIP-1193 provider + EIP-712 typed data) จึงไม่ต้องเลือกครั้งเดียวตลอดไป
