1. ภาพรวมและเหตุผลการเลือก OCI

ทำไม OCI

• Always Free: Ampere A1 4 OCPU/24 GB + 2 Micro VMs + 200 GB storage + LB — พอสำหรับ Stage 0 ทั้งระบบที่ $0
• egress 10 TB/เดือนฟรี เหมาะกับ RPC/indexer traffic
• OKE Enhanced + Workload Identity, managed PostgreSQL, Vault (HSM) สำหรับ Lean Phase-1
• Cloud Guard / Security Zones / Audit ช่วยผ่าน compliance baseline เร็ว

Design drivers

• Signer แยก network เสมอ (VM แยกใน Stage 0, node pool + subnet แยกใน Lean)
• Postgres เป็น stateful service เดียว (queue · outbox · locks) — ไม่มี Redis/Kafka/Temporal จนถึง trigger
• Everything-as-code (Terraform + GitHub Actions; Argo CD ใน Lean)
• Cold DR ที่ scripted: RPO ≤ 15 นาที, RTO 2–4 ชม. (เชนเป็น system of record)

สิ่งที่ ไม่ อยู่บน OCI

• Edge: Cloudflare Free (DNS, WAF, Pages, Tunnel) — ADR-008
• Blockchain networks, RPC providers (free/growth tier; own node ที่ T4)
• LLM ของผู้ใช้เอง (BYO key, client-side), data feeds ฟรี, Telegram Bot API
• User keys (อยู่ใน wallet ผู้ใช้เสมอ)

10. CI/CD & GitOps

  • Deploy strategy: core/exec = rolling (Stage 0) / Rollouts canary + auto-rollback (Lean); signer = blue/green ด้วย readiness ที่เซ็น test vector + ตรวจ allowlist config hash ตรงกับ Git; job worker drain ก่อน swap (payload มี schema_version)
  • Promotion: CI (tests/fuzz/slither/evals/import-linter) → e2e บน Anvil (จาก simulations/) → ephemeral staging (Base Sepolia) ผ่าน ops-staging.yml soak 24h → prod ด้วย GitHub Environment required reviewer (1 คลิก)
  • Rollback: revert digest bump PR → pull deploy (< 5 นาที); DB migration ต้อง backward-compatible (expand/contract)
  • Dependencies: Renovate PR อัตโนมัติ (images, Helm, Terraform providers, Foundry, Python/Go deps); auto-merge minor/patch เมื่อ CI เขียว; major ต้อง review
  • Canary user: delegation ของบริษัท 1 USDC/สัปดาห์บน mainnet — ถ้าไม่ settle ภายใน period = alarm Critical (end-to-end probe รวมเชนจริง)
  • Contracts: release-contracts.yml สร้าง bundle (bytecode hash, args, CREATE2 address) → คนเซ็น 1 tx จาก hardware wallet → workflow verify on-chain bytecode, verify source บน explorer, gen ABI ลง packages/sdk, เปิด PR อัปเดต addresses

Load shedding & degradation order (เมื่อ backlog โต)

  1. ลดความถี่ macro indicators (15 → 60 นาที) — snapshot ยัง fresh ตาม maxAge
  2. เพิ่ม batch size และ interval ของ settleBatch
  3. เปิด waitlist (หยุด delegation ใหม่) — ผู้ใช้เดิมไม่กระทบ
  4. ไม่มีขั้น "ข้ามการซื้อ" โดยอัตโนมัติ — ถ้าถึง window end จริงจึงเป็น SKIP(reason=CAPACITY) และ alarm Critical

พิสูจน์ด้วย load test ไม่ใช่ความเชื่อ

  • loadtest.yml (workflow_dispatch): ephemeral staging + Anvil ที่ seed 100k synthetic delegations → รัน 1 period จำลอง (time-warp) → วัด jobs/s, p95 decision→submit, settle success, DB CPU, RPC CU ต่อ user
  • ผลลัพธ์เก็บเป็น baseline ใน repo; regression > 20% = block release
  • Capacity alarms (หัวข้อ 9) ผูกกับตัวเลขจาก baseline ไม่ใช่ตัวเลขคาดเดา; trigger T1/T2/T4 อ้างอิง baseline นี้
สรุป: ส่วนที่เป็นของเรา (core/exec/signer/queue) auto-scale ได้ตั้งแต่ Lean และมี headroom ถึงหลักล้าน users ด้วย settleBatch + per-user offset; สิ่งที่จะ "ตาย" ก่อนคือ RPC plan, allowance cap และ issuer onboarding — ทั้งสามมี alarm + lever ในตารางข้างบน
